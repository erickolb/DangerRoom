# AWS S3 cover storage

DangerRoom supports `local` (default) and `s3` for newly downloaded covers. Comic metadata and the SQLite database always stay in `DATA_DIR`. Images keep stable `/covers/<sha256>.<extension>` URLs; the server reads private S3 objects on behalf of the browser. **Public read access is not required or recommended.** Keep all S3 Block Public Access settings enabled and Object Ownership set to Bucket owner enforced (ACLs disabled). No bucket CORS configuration is needed because browsers contact DangerRoom, not S3.

## Configuration

Install dependencies with `pnpm install --frozen-lockfile`. Set these in the ignored `.env`, then restart the server:

```dotenv
IMAGE_STORAGE=s3
AWS_REGION=us-east-1
S3_BUCKET=your-unique-bucket-name
S3_PREFIX=dangerroom/covers
```

| Option | Default / purpose |
| --- | --- |
| `IMAGE_STORAGE` | `local` or `s3`; determines where new covers are written. |
| `DATA_DIR` | `./data`; local SQLite and any existing local covers. |
| `AWS_REGION` | Required for S3, including migration. Use the bucket's region. |
| `S3_BUCKET` | Required for S3; bucket name, not an ARN or URL. |
| `S3_PREFIX` | `dangerroom/covers`; optional object key prefix. Empty means bucket root. Leading/trailing slashes are removed. |
| `AWS_PROFILE` | Optional named profile from the standard AWS shared configuration files. |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Alternative server-only credentials; prefer an IAM role on AWS. |
| `AWS_SESSION_TOKEN` | Required when using temporary access-key credentials. |

The AWS SDK's standard credential chain supports environment credentials, shared profiles and workload/instance roles. Never put credentials in frontend code or commit `.env`. No custom endpoint, public URL, ACL, or automatic bucket creation option is provided. Use a general purpose AWS S3 bucket with default encryption. If using a customer-managed KMS key, also grant the required KMS permissions; SSE-S3 needs no separate KMS configuration.

Create the bucket yourself in the chosen region. Grant the app's IAM principal this policy, substituting your bucket and prefix:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::your-unique-bucket-name/dangerroom/covers/*"
  }]
}
```

No public bucket policy, `ListBucket`, delete permission, or ACL permission is needed. If the prefix is empty, the resource ends in `/*`. Cross-account deployments may additionally need a bucket policy granting the same principal access. Use a separate prefix per independent collection. The app never deletes S3 objects. Consider versioning and an appropriate backup policy; avoid lifecycle rules that expire active images or move them into archival tiers requiring restore.

## One-time local to S3 migration

The operator command is `scripts/migrate-covers-to-s3.mjs`. It uses the same `.env` and AWS credentials as the app; it does not contact Metron.

1. Stop DangerRoom and back up the entire `DATA_DIR` and configuration. Run from the repository root. Keep the app stopped until migration completes.
2. Configure the target bucket, region, credentials, and prefix above. The utility forces S3 mode even if `IMAGE_STORAGE` is still `local`.
3. Preview files without uploading or changing their locations:

   ```sh
   pnpm run migrate:covers:s3 --dry-run
   ```

4. Run the migration:

   ```sh
   pnpm run migrate:covers:s3
   ```

5. Set `IMAGE_STORAGE=s3`, restart with `pnpm start`, and check several owned and wanted covers. With no downloaded covers, the command succeeds with zero images.

The utility scans all content-addressed local cover files, including retained covers, and checks database references for missing files. Each upload includes a SHA-256 checksum and is downloaded again for byte verification. Only then is its bucket/key recorded in `cover_objects`. Edition and Want List filenames stay unchanged and share one location for identical image bytes. Local files are **never deleted**. A failure stops the run with a nonzero exit status; rerun to skip completed images and retry remaining ones. An upload completed before an interruption may be safely uploaded again at the same key. Dry runs can create/upgrade the database schema but do not alter image locations.

Already migrated images are skipped, even if you later change bucket/prefix. This utility migrates local images only; it does not relocate existing S3 objects. Changing `IMAGE_STORAGE` back to `local` changes new writes only: recorded S3 objects still require AWS access. Existing local images remain readable in S3 mode until migrated. To roll back entirely, restore the stopped-app database backup with its matching local files, or implement a separate S3-to-local migration; changing the mode alone is not a rollback.

## Operation and backups

New inventory/want entries are saved only after their cover upload and verification succeed. Missing provider covers still use the usual placeholder. Failed S3 reads return an error without silently serving a different cover. Retained originals are not automatically cleaned up after copy/want removal.

Back up SQLite while the app is stopped, any remaining local covers, S3 objects, and the bucket/prefix configuration together. Database location records are essential: backing up only the bucket is insufficient. The migration preserves local copies so you can verify your S3 setup before making any manual storage cleanup decision. Deployment on another host requires the database, matching object access, dependencies, and environment configuration.

References: [AWS Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), [S3 security best practices](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html), and [AWS SDK credential providers](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/setting-credentials-node.html).
